# Domain Knowledge Agent Framework 项目进度汇报

> 汇报周期：2026-09-01 至 2026-09-02
>
> 当前阶段：框架骨架完成，进入 Agent 业务契约和真实场景验证阶段

## 1. 本阶段结论

项目已经从方案设计推进到可运行的 LangGraph 多 Agent 框架。7 类 Agent 都进入了实际图结构，文档生成、测试生成、代码生成、检查、评测、审查和发布链路可以完整跑通；并行分发、循环修订、回滚、失败终止、Artifact 校验和 Checkpoint 恢复也有自动化测试覆盖。

公司环境的接入边界已经落实：核心包通过 CodeAgent CLI 调用内部 Agent，不直连底层模型 API；Codex 只保留在独立的可选 Provider 包中，不会进入公司的安装依赖和发布包。

现阶段完成的是“框架能否可靠编排和替换 Agent 后端”的验证，还不能等同于知识生成质量已经达标。各 Agent 的 Prompt、业务 Schema、源码分块方法和真实质量指标仍需结合目标项目确定。

## 2. 已完成工作

### 2.1 顶层编排

- 使用 TypeScript 和 LangGraph 建立唯一的顶层编排图；
- 保留 Orchestrator、DocWorker、DocGen、TestGen、Code、Check、Review 7 类 Agent；
- DocWorker 通过 `Send` 按 worker 数量并行分发，TestGen 与文档链并行执行，并在 EvalRunner 前汇合；
- Gate 使用确定性代码处理 `pass`、`iterate`、`rollback`、`stopped` 和 `failed`，Agent 不能绕过门禁直接发布；
- 有效的业务评测结果必须经过 Review，基础设施错误则直接失败，避免生成误导性的业务结论。

### 2.2 运行、恢复和产物管理

- 提供 Service API 和 CLI，支持运行、恢复、状态查询、取消和 Artifact 查询；
- 默认使用 SQLite 保存 Checkpoint，测试可切换到内存实现；
- 跨节点产物写入 `.agent-runs/{runId}`，记录 SHA-256、生产节点和 completion marker；
- 每个节点使用独立工作目录和读写策略，已能发现路径越界与产物篡改；
- Fake Runner 可注入延迟和失败，用于稳定复现并行、循环及异常场景。

### 2.3 Agent 后端和部署隔离

- `AgentRunner` 接口把图编排与具体 Agent 后端分开，替换 Runner 不需要修改图；
- 公司运行时已接入 CodeAgent CLI，覆盖登录状态检查、非交互执行、会话恢复、超时终止、错误分类和文件快照；
- Code、Check、Review 等节点按职责配置工具白名单，Check 和 Review 保持只读；
- Codex SDK 已移到 `providers/codex` 独立包，根包 manifest、锁文件、核心源码、构建产物和 npm 发布包均不包含 Codex 依赖。

### 2.4 文档和验收材料

- 已形成整体框架设计、验收方案、知识回写治理、决策记录和部署隔离说明；
- 新增 Agent 输入输出总览，列出每类 Agent 的最小输入、输出、证据要求和禁止边界；
- 自动化测试覆盖拓扑、路由、并行、Checkpoint、Artifact、Adapter、CLI Runner 和命令评测器。

## 3. 最新问题处理

真实 CodeAgent 执行 DocGen 通常需要 2 至 3 分钟。原图节点超时固定为 120 秒，外层 LangGraph 会在 CodeAgent 自身的 300 秒超时之前终止任务，因此出现 Fake Runner 正常、真实 Agent 超时的差异。

本次已将图节点默认超时调整为 600 秒，并抽取 CodeAgent 的 300 秒默认超时常量。回归测试会检查图节点超时必须高于 Runner 超时。这样仍由 CodeAgent Runner 负责判断自身超时，LangGraph 只处理更外层的卡死保护。

如果后续把 `--codeagent-timeout-ms` 设置到 600 秒以上，还需要同步提供图节点超时配置，避免出现新的倒挂。该项已列入后续配置治理。

## 5. 当前风险和边界

| 事项 | 当前情况 | 影响 |
|---|---|---|
| Agent 业务契约未定稿 | Prompt、业务 Schema、ContextBuilder 仍在讨论 | 无法开始稳定的知识质量对比 |
| 工作区隔离强度有限 | 已有目录和权限策略，但不是容器或虚拟机级强制隔离 | 真实 CodeAgent 上线前需要补越权探针和运行环境约束 |
| 测试 Oracle 流程待细化 | 候选测试、人工复核和受保护门禁集的进入规则未定 | 可能把错误期望写入测试基线 |
| 真实 Agent 覆盖不足 | 当前主要依靠 Fake Runner，CodeAgent 只验证代表节点 | 真实并发、长任务、限流和恢复仍可能暴露问题 |
| 超时配置尚未统一 | 默认值已修复，但图超时还不能随 CLI 参数联动 | 自定义超时时需要人工保持配置一致 |
| 本地存储面向单实例 | SQLite 和本地 ArtifactStore 适合 V1 | 多人共享、跨实例调度和云端存储暂不支持 |

## 6. 下一阶段计划

下一阶段建议先把一个真实业务样例跑深，不急于扩展更多 Provider。

1. 选定目标代码库和一个边界清晰的模块，冻结公开接口、真实源码范围及验收测试。
2. 定稿 DocWorker、DocGen、TestGen、Code、Check、Review 的最小业务 Schema，同时明确 DocGen 是否可以定向补读源码。
3. 建立首个固定数据集，记录知识事实覆盖率、引用溯源、Oracle 正确率和 held-out test 通过率。
4. 完成 CodeAgent 全链路小规模联调，重点测试两路并发、长任务超时、会话恢复、取消和权限失败。
5. 将图节点超时做成运行时配置，并与 CodeAgent Runner 超时建立校验关系。
6. 补齐物理隔离探针和剩余验收场景，再决定是否引入容器级沙箱。

## 7. 需要确认的事项

为了不让框架默认值变成事实标准，下一阶段开始前需要确认以下内容：

- 首个真实样例使用哪个仓库、模块和目标语言；
- DocGen 的源码读取边界，以及 TestGen 产出的测试如何进入门禁集；
- CodeAgent 的 `--bare` 和跳过权限模式是否允许用于公司自动化任务；
- Check/Review 的 blocking 判据和报告 Schema；
- 业务质量达到什么条件才允许知识从候选区发布到已验证区。

## 8. 阶段判断

框架骨架已达到可演示、可测试、可替换 Runner 的状态，公司依赖隔离也通过了自动校验。下一阶段的主要工作不再是增加图节点，而是把真实业务输入、Agent 契约和质量门槛定下来，并用固定样例验证整条链路。
