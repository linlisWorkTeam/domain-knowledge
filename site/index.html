知识证据链

从知识结论一路返回产生它的证据

知识健康度、版本血缘和差异已经成为可查询事实。可以从版本进入关联批次、评测报告、纠正记录和发布凭据。

  • 总分与分项口径由服务端计算
  • 差异范围经过修订约束校验
治理资源

评测和来源都有独立生命周期

评测报告、证据工件与规则修订可以复核；来源可以登记、筛选、刷新、识别漂移和停用，历史记录不会被直接删除。

  • 规则新修订只影响后续评测
  • 来源刷新保留审计与幂等结果
运行与效果

速度、成本和治理效果放在一起看

运行观测给出批次、节点和排队耗时，以及调用、Token、成本与重试；治理效果继续跟踪收敛、人工介入和短期复发。

  • 所有统计同时显示样本量与窗口
  • 无样本时明确显示为空，不推测结果

为什么需要知识飞轮

写得像答案，
不代表真的能用。

知识飞轮不只保存结论。它还记下结论怎么被验证、失败后改了哪里，以及最后是谁按规则放行。

未经行为验证候选

看起来像答案

有结构、有来源、质量门禁通过，但还没有独立执行证据。它可以进入评测，不能直接进入正式查询结果。

  • — 文档质量 ≠ 行为正确
  • — 智能体自评分 ≠ 独立证据
  • — 单次成功 ≠ 稳定可复用

信任边界

有些事，
它现在还做不到。

01固定项目验收只面向受信源码，不是用来运行敌对代码的系统沙箱。

02确定性夹具只能证明编排正确；一次真实运行也不能证明模型长期稳定。

03网页控制台默认只读，普通智能体没有自行发布权限。

04发布门禁只接受完整、匹配且可以校验的独立证据。

05智能体只能追加提示词；职责、输入输出、拓扑与工具权限不可替换。

06代码生成角色由当前智能体提供方执行，并通过文件白名单和系统级隔离避开参考源码；这并不等于具备敌对代码沙箱。

智能体任务 · 配置知识飞轮 
请从 0 到 1 配置并启动知识飞轮。你需要实际执行命令、处理可安全修复的问题，并在最后给出可核对的结果。

仓库：https://github.com/linlisWorkTeam/domain-knowledge

执行要求：
1. 如果当前目录已经是 domain-knowledge，先检查 git status，保留所有未提交改动；否则克隆仓库并进入目录。不要覆盖用户文件。
2. 阅读 README.md、CONTRIBUTING.md、docs/GETTING_STARTED.md 和 specs/README.md。
3. 检查 Git、Node.js 和 npm。Node.js 必须是 24 或更高版本；版本不满足时，使用机器已有的版本管理器升级，并说明改了什么。
4. 执行 npm ci、npm run typecheck、npm run validate:specs、npm test。任何门禁失败都要先定位原因；不得跳过测试、降低阈值或伪造通过结果。
5. 使用独立运行目录初始化：
   WP_FLYWHEEL_HOME=.workpanel npm run knowledge -- init
   WP_FLYWHEEL_HOME=.workpanel npm run knowledge -- status
6. 以只读模式启动控制台：
   WP_FLYWHEEL_HOME=.workpanel npm run knowledge:serve
   检查 http://127.0.0.1:4174/health，并确认首页可访问。
7. 除非我明确要求公网访问，否则只监听 127.0.0.1。不要设置 WP_KNOWLEDGE_WRITE_TOKEN，不要把令牌、数据库、内容寻址存储或 .workpanel 提交到版本库。
8. 不得手工把候选状态改成已验证，不得调用已经退休的评分、评测或摄取命令，也不得把确定性夹具写成真实模型质量证明。
9. 最后报告：实际 Node/npm 版本、运行过的检查及结果、服务 PID、访问地址、运行目录、git status，以及仍未解决的问题。若服务无法启动，保留完整错误摘要并给出下一步。
