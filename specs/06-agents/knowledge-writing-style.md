# 知识写作风格

## 目标

知识是写给下一位工程师看的。他通常正带着一个具体问题来到这里，不需要一段宏大的开场，也不想从宣传词里猜真正的限制。

DocGenAgent 首次生成和按 Correction 修订时，必须收到同一份版本化写作约束。当前实现位于 `src/application/services/knowledge-writing-guide.ts`，规则参考 [Humanizer-zh](https://github.com/op7418/Humanizer-zh)，并针对工程知识收紧。

## 写法

1. 开头直接给出结论和适用条件。
2. 用接口、命令、数值、失败现象和 SourceRef 支撑判断。
3. 解释原因。不要只罗列步骤，也不要把源码换一种说法。
4. 句子可以有长有短。能用“是”“有”“会”说清楚时，不使用绕口的宣传表达。
5. 不确定就写清楚缺少哪项证据，不用“专家认为”“行业报告显示”代替来源。
6. 标题帮助查找，不追求整齐的三段式；列表只在并列内容确实需要时使用。

## 避免的模式

- “综上所述”“值得注意的是”“随着……发展”等填充连接词；
- “至关重要”“赋能”“全方位”“不断演变的格局”等没有证据的判断；
- 机械三段式、连续同构句、过多破折号、表情符号和粗体；
- 为了显得自然而虚构第一人称经历、情绪、数字、引用或用户反馈；
- 把 `CANDIDATE`、质量合格、Gate `PASS` 和 `VERIFIED` 写成同一个概念。

## 优先级

自然表达服务于理解，不能凌驾于真实性。发生冲突时，优先保留：

1. 可核对的事实与 SourceRef；
2. 契约术语、命令和精确数值；
3. 适用条件、失败分支和安全边界；
4. Schema 与 Correction 指定的结构；
5. 最后才是语气和节奏。

Spec、Schema、审计事件和安全策略允许保留重复、枚举和规范词。它们首先要可机器检查或无歧义，不以“像人聊天”为目标。

## 确定性检查

Quality Gate 提供 `humanReadability` 信号。当前检查只识别高置信度问题：

- 公式化填充或宣传词反复出现；
- 非代码段落过长，读者难以定位结论。

低分会产生 `readability` weak point，并影响候选质量分。它不是行为正确性证明，也不能单独让知识成为 `VERIFIED`。更细的语义判断仍由 DocGen Prompt、Review 和人工评审完成。

## 验收

`AC-DOC-001` 要求：

- 首轮生成和 Correction 修订都收到写作约束；
- 模板化中文能被确定性策略识别；
- 正常、具体且有来源的知识不受惩罚；
- 风格修订不能越过 Correction 指定范围，也不能改变发布门禁。
